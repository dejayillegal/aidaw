# ADR-004 — Canonical audio settings and recoverable project snapshots

Status: proposed correction, implemented on the report-containing branch. Retains ADR-002/ADR-003, existing command bus, state contracts, timeline helpers, XML engine and audio engines.

## Confirmed deficiencies

App-owned humanization/master/transport settings were separate from command snapshots. History inspection exposed writable undo state. Queue inspection exposed working state. Humanizing a track regenerated clip zero and collapsed other independent clips. Native schema validation accepted malformed required controls. Background IndexedDB writes had no validated startup recovery contract. The checksum helper silently returned a non-SHA fingerprint when Web Crypto failed.

## Decision

`AbletonProjectState.audioSettings` owns humanization, master bus and transport preferences. Arrangement extent remains the existing root field; the transport view derives it. Queued calibration/export prefer each project’s settings over another active project’s controls. UI edits transact through the existing bus outside React updater functions. Queue snapshots are isolated, with immutable Blob references shared. History snapshots are isolated. XML is a projection plus retained opaque source, never an independent authoritative score.

Native project format v2 serializes settings once, inside project. Version1 migrates its root settings; ambiguous ownership and future versions reject. Decode validates state and settings before installation and rebuilds the XML projection. Empty native projects load directly as canonical state rather than passing through an ALS parser that requires tracks. No assets or undo stack are embedded.

The existing IndexedDB store journals versioned, SHA-256 checked queue records. Serialized writes atomically rotate the previous record and store its successor in one transaction. Completion/abort is awaited. Boot validates identity, checksum and domain state, rebuilds stale XML, and can recover a previous valid revision. Unsupported future primary records are preserved without silent downgrade. Removed entries cannot be resurrected by delayed work. Unknown future journals block starter initialization in the actual UI; records are preserved. Write failures are visible; an in-memory edit is not described as durably saved.

Humanization now transforms existing event timing/velocity in place, preserving clip schedules, note identity/pitch/probability and devices. Repeated transforms use stored base velocity/grid time. Generated browser-only devices are explicitly marked as such when app-created MIDI tracks are materialized in XML; this is not native Ableton device hosting.

## Consequences and limitations

No second domain, composition engine, clock or renderer. Existing beat-based time remains: integer ticks and tempo/meter maps are still outstanding. Scene application remains an undoable Arrangement replacement, not live Session launching. Recovery is a previous-revision journal, not an asset backup or guarantee against browser storage eviction. Strict schema validation is stronger for supported fields, not a complete future-proof schema for every unsupported ALS structure.

## Rollback / migration

Retain original v1/native/ALS files before upgrade. Revert this branch to the verified M2 main baseline for code rollback. M2 cannot read v2 native files or versioned recovery envelopes; export supported ALS before rollback or retain the upgraded reader to recover v2 data. Do not silently downgrade by deleting version checks. No claim of lossless universal v2-to-v1 conversion. Atomic journaling keeps prior state on a failed write; corrupt-primary fallback and future-version refusal require real IndexedDB CI evidence.
